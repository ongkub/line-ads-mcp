# รูปแบบไฟล์ Customer List Audience

ใช้กับ [MODE 8](../workflows/08-customer-list-audience.md) ก่อนเรียก `upload_customer_list`
กฎการรับ/ตรวจไฟล์และผลตอบกลับด้านล่างยึด tool contract; ไม่ใช่ให้ผู้ใช้ส่งข้อมูลดิบมาในแชท

## เตรียมไฟล์ในเครื่อง

- ใช้ CSV UTF-8 หรือ TXT หนึ่งรายการต่อบรรทัด; แนะนำหนึ่งคอลัมน์ หนึ่งชนิดข้อมูลต่อไฟล์ มี header ได้
- Excel/Google Sheets: export/download เป็น CSV UTF-8 ก่อน; `.xlsx` ต้องแปลงก่อนใช้ tool
- ตั้งคอลัมน์เบอร์เป็นข้อความเพื่อรักษา 0 นำหน้า หลีกเลี่ยงสูตร/รูปแบบ scientific notation ที่ทำเลขเสีย
- แจ้ง absolute path บนเครื่องที่ MCP เข้าถึง ไม่แนบไฟล์ดิบหรือคัดรายชื่อลงแชท
- ชื่อคอลัมน์ auto-detect: phone/tel/mobile/เบอร์/โทร, email/อีเมล, ifa/adid; ถ้ากำกวมระบุ `column` เอง
- `default_country_code="66"` สำหรับไทย; ประเทศอื่นต้องระบุรหัสให้ถูก ถ้าปนหลายประเทศให้แยกไฟล์หรือเตรียมเลขพร้อมรหัสประเทศ
- tool ตัดรายการว่าง/ซ้ำ แล้วรายงาน counts และตัวอย่างที่ปิดบังแล้ว ไม่คืน/เก็บค่าดิบ

## กฎตามชนิด ID

ตัวเลขและอีเมลด้านล่างเป็น **(ตัวอย่างสมมติ)** สำหรับอธิบายรูปแบบ ไม่ใช้ข้อมูลลูกค้าจริงในเอกสารหรือแชท

| `id_type` | รูปแบบที่รับ/การ normalize | ตัวอย่างสมมติ: valid / invalid → ผล |
|---|---|---|
| `PHONE` | รหัสประเทศ + หมายเลข เป็นตัวเลขล้วน; ตัด + ช่องว่าง/ขีด และเปลี่ยน 0 นำหน้าเป็นรหัสประเทศที่ระบุ | valid: `081-234-5678` หรือ `+66 81 234 5678` → `66812345678` |
| `PHONE` | ห้ามเดาเลขที่ขาดหรือประเทศจากความยาวเพียงอย่างเดียว | ต้องตรวจต้นทาง: `812345678` (9 หลัก อาจขาด 0) → ไม่เดาเติม; invalid: `08abc` → แก้/ตัดออก |
| `EMAIL` | trim ช่องว่างหัวท้าย + lowercase; ยาวไม่เกิน 120 ตัวอักษร และต้องเป็นอีเมลถูกแบบ | valid: ` Demo@Example.com ` → `demo@example.com`; invalid: `demo@` หรือยาวเกิน 120 → แก้/ตัดออก |
| `IFA` | Advertising ID รูป UUID; normalize เป็น lowercase UUID ไม่ hash เหมือน PHONE/EMAIL | valid: `A1B2C3D4-1234-4ABC-8DEF-1234567890AB` → `a1b2c3d4-1234-4abc-8def-1234567890ab`; invalid: `customer-001` → ใช้ไม่ได้ |

ถ้า dry-run ยอมรับค่าที่น่าสงสัย เช่น เบอร์ 9 หลัก ให้ผู้ใช้ตรวจต้นทางก่อน ไม่ถือว่าผ่านรูปแบบแล้วข้อมูลจริงถูกต้อง
ไม่ให้ AI เปิดไฟล์เพื่อหาค่าดิบเพิ่ม ใช้ masked samples และเลขแถวที่ tool คืนเพื่อให้เจ้าของไฟล์แก้ในชีต

## ทำไมต้อง Hash

PHONE/EMAIL ถูก normalize แล้ว hash **SHA-256 เป็น lowercase hex** ในเครื่อง/หน่วยความจำก่อนส่งให้ LINE จับคู่กับ hashes ของผู้ใช้ จึงไม่ต้องส่งเบอร์หรืออีเมลดิบไปใน upload
IFA ใช้ UUID ตามรูปแบบ ไม่ hash แบบ PHONE/EMAIL
ห้าม hash ซ้ำเอง; `prehashed` ใน dry-run บอกจำนวนค่าที่ tool ตรวจพบว่า hash แล้ว แต่ไม่ยืนยันว่ารูปแบบก่อน hash ถูกต้อง
Hash ไม่แทนความยินยอมหรือทำให้ข้อมูลใช้โฆษณาได้โดยไม่มีฐานกฎหมาย และไม่ควรวาง hashes ทั้งชุดในแชท

## ขนาดไฟล์และจำนวนรายการ

[เอกสาร Treasure Data LINE connector](https://docs.treasure.ai/int/line-ads-custom-audience-export-integration) ระบุขีดจำกัด **62,914,560 bytes ต่อ upload (60 MB)** ประมาณ 0.9 ล้านรายการสำหรับ hashed phone/email; เป็นค่าประมาณตามความยาวรายการ ไม่ใช่จำนวนรับประกัน
เช็ก `file_bytes` และ `within_size_limit` จาก dry-run จริงก่อนส่ง ถ้าเกินให้แบ่งไฟล์แล้วตรวจแต่ละไฟล์ใหม่ ไม่สมมติว่า tool แบ่งไฟล์อัตโนมัติเหมือน connector
ถ้าสร้างฐานจากหลายไฟล์ ให้ใช้ฐาน ID ที่ได้จากไฟล์แรก แล้ว **ADD** ไฟล์ถัดไป; REPLACE รอบถัดไปจะแทนที่ชุดก่อนหน้า

## ADD กับ REPLACE

| ตัวเลือก | ผล | ก่อนส่งจริง |
|---|---|---|
| `audience_name` + ADD | สร้างฐานใหม่ | สรุปชื่อ/ชนิด/จำนวน แล้วรอ “ยืนยัน” |
| `audience_id` + ADD | เพิ่มรายการในฐานเดิม | ตรวจ ID จริง สรุป แล้วรอ “ยืนยัน” |
| `audience_id` + REPLACE | แทนที่สมาชิกเดิมทั้งหมดด้วยไฟล์นี้ | เตือนผลกระทบและขออนุมัติ REPLACE ชัดเจน |

ส่ง `audience_name` หรือ `audience_id` อย่างใดอย่างหนึ่ง; ใช้ dry-run ก่อนเสมอ
การยืนยันหนึ่งไฟล์/action ไม่อนุมัติการส่งไฟล์อื่นหรือเปลี่ยน action

## หลังส่งและการอ่านขนาด

- รับ upload แล้วฐานใหม่เริ่ม IN_PROGRESS; ติดตาม `get_customer_list_upload_status(audience_id)` จน `done` และดู job_status/failed_type ตามจริง
- FINISHED ของงาน upload ยังไม่เท่ากับใช้ฐานได้ ต้องตรวจ `list_audiences` จน READY และ `usable_in_adset=true`
- `estimated_audience_size="-"` = เล็กเกินรายงาน; `"100 or fewer"` = ไม่เกิน 100 คน ไม่ใช่จำนวนแน่นอน
- จำนวน valid/hashed records ไม่ใช่จำนวนที่ match; **match rate ยังไม่ทราบจนประมวลผล** ไม่รับปากเปอร์เซ็นต์ และไม่เรียกขนาดประมาณว่า match rate ที่แน่นอน
- ถ้าผลผิดพลาดให้ดู failed_type/status จริง ไม่แก้ด้วยการ upload ซ้ำหรือ REPLACE อัตโนมัติ

## PDPA และการใช้ข้อมูลเท่าที่จำเป็น

ถามก่อนใช้ไฟล์ว่าลูกค้ายินยอมหรือธุรกิจมีฐานกฎหมายรองรับการใช้ข้อมูลเพื่อโฆษณาหรือไม่; ถ้าไม่แน่ใจให้หยุดและตรวจสอบกับ DPO/ฝ่ายกฎหมาย
ใช้เฉพาะคอลัมน์ที่จำเป็น เก็บไฟล์ไว้กับเจ้าของข้อมูล ไม่แชร์ไฟล์ดิบในแชท และแสดงเฉพาะ masked samples จาก tool
คำแนะนำนี้เป็นแนวปฏิบัติ ไม่ใช่คำปรึกษากฎหมาย; ห้ามสรุปว่า “มีไฟล์ = มีสิทธิใช้”

## แหล่งอ้างอิงและข้อควรตรวจ

- [LINE Ads API v3.12.3 — Custom Audiences](https://ads.line.me/public-docs/v3/3.12.3/certificated-ad-tech-general-partner) — อ้างอิง API upload และสถานะ audience; ชื่อ params ของ MCP ใช้ตาม tool contract
- [Treasure Data LINE Ads Custom Audience Export Integration](https://docs.treasure.ai/int/line-ads-custom-audience-export-integration) — ยืนยันขีดจำกัด bytes และการ auto-hash phone/email; กฎตัด `+`/SHA-256 ด้านบนยึด tool contract ที่กำหนด (หน้าอ้างอิงที่อ่านได้ไม่แสดงรายละเอียดนี้); ขั้นตอนเชื่อมต่อ/แบ่งไฟล์ของ connector ไม่ใช่พฤติกรรม MCP
- **ยืนยันรูปแบบด้วยไฟล์ทดสอบเล็กก่อนใช้งานจริง** โดยใช้ข้อมูลที่มีสิทธิใช้ และทำ dry-run → สรุป → “ยืนยัน” ก่อน upload เช่นเดียวกัน
